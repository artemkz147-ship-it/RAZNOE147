# Постоянные правила проекта RAZNOE147

Этот репозиторий используется для совместной разработки игр и Android-приложений с помощью ChatGPT и GitHub. Эти правила являются базовыми для всех новых работ в репозитории.

## 1. Отдельная ветка на каждый проект

- Каждая новая игра или приложение разрабатывается в отдельной Git-ветке.
- `main` не используется как рабочая ветка конкретной игры/приложения.
- Ветка должна иметь понятное имя по проекту, например: `mobile-racing`, `reader-app`, `reels-downloader`.
- Не смешивать код, ассеты и зависимости разных проектов в одной ветке без явного указания пользователя.

## 2. GitHub можно и нужно использовать как источник технологий

Разрешено искать и использовать подходящие open-source решения с GitHub: библиотеки, плагины, движки, модели машинного обучения, нейросети, TTS/STT, рендеринг, физику, обработку изображений/аудио, форматы файлов и другие компоненты, если они реально улучшают продукт.

Перед включением зависимости обязательно проверить:

- что она бесплатна для требуемого использования;
- что лицензия разрешает использование и распространение внутри приложения/APK;
- что она технически совместима с целевой платформой Android;
- что она не требует скрытой платной подписки, платного API или обязательного внешнего сервиса;
- что размер, производительность и требования модели/библиотеки приемлемы для мобильного устройства.

Предпочтительные лицензии: MIT, Apache-2.0, BSD и другие permissive-лицензии. Компоненты с copyleft/GPL и похожими обязательствами использовать только если их условия действительно совместимы с проектом и последствия лицензии понятны.

## 3. Нейросети и модели должны работать у конечного пользователя

По умолчанию допускаются только такие нейросети/модели/компоненты, которые можно законно встроить в приложение или поставить вместе с ним так, чтобы обычный пользователь получил рабочую функцию после установки APK.

Приоритет: локальный inference на устройстве, bundled assets/models, ONNX/TFLite/NCNN/llama.cpp и аналогичные автономные варианты, если они подходят задаче.

Нельзя выдавать за «встроенную бесплатную нейросеть» решение, которое на самом деле требует:

- личного API-ключа;
- платного тарифа;
- нашего постоянно работающего сервера;
- регистрации разработчика у стороннего сервиса;
- ручной настройки пользователем после установки.

Если полезная функция технически требует интернет, внешний сервер, API или скачивание модели после установки, это нужно явно сказать пользователю ДО того, как считать функцию реализованной. Без явного согласия пользователя такие зависимости не являются базовым решением.

## 4. Никакого вранья о готовности

Нельзя утверждать, что функция, сборка, APK, тест или интеграция работают, если это не было реально выполнено или проверено доступными инструментами.

Если что-то невозможно сделать в текущей среде, нужно прямо написать:

- что именно невозможно;
- почему;
- что уже сделано;
- какой конкретный шаг или доступ нужен для завершения.

Нельзя подменять готовый результат заглушкой и называть её готовой функцией. Заглушки допустимы только как промежуточный этап и должны быть явно помечены.

## 5. Целевой результат — устанавливаемый APK

Для Android-проекта работа не считается полностью завершённой только потому, что написан исходный код.

Финальная цель:

1. исходники проекта находятся в его отдельной ветке;
2. зависимости зафиксированы;
3. проект собирается воспроизводимо;
4. выполняется хотя бы базовая проверка запуска/сборки;
5. собирается APK;
6. пользователю передаётся готовый APK либо реальный GitHub Actions artifact/release, из которого APK можно скачать.

Если APK физически не удалось собрать, нельзя писать «готово». Нужно назвать точную причину сбоя сборки.

## 6. Сборка без лишней ручной возни

Предпочтителен полностью воспроизводимый build pipeline через CLI/Gradle/GitHub Actions или другой подходящий автоматизированный способ. Не требовать от пользователя Android Studio, ручного редактирования проекта или установки большого набора инструментов, если этого можно избежать.

Секреты, токены и приватные ключи никогда не коммитить в репозиторий. Если они нужны для подписи/release, использовать GitHub Secrets или другой безопасный механизм.

## 7. Качество продукта

По умолчанию делать не демонстрационный прототип, а максимально полноценный продукт в рамках задачи:

- нормальный мобильный интерфейс;
- адаптация под разные размеры экранов и системные панели;
- обработка ошибок и крайних случаев;
- отсутствие очевидных падений;
- разумное потребление памяти и батареи;
- отсутствие ненужных разрешений;
- корректная работа без сети там, где заявлен офлайн-режим;
- никаких финальных placeholder-экранов/ассетов, если пользователь не просил прототип.

## 8. Проверка стороннего кода

Нельзя бездумно копировать случайный репозиторий. Для внешних компонентов по возможности проверять актуальность, лицензию, зависимости, известные проблемы, Android-совместимость и риск заброшенности проекта. Версии зависимостей фиксировать, чтобы сборка не ломалась от случайного обновления.

## 9. Принцип работы

Сначала искать самый сильный практически реализуемый вариант. Если бесплатный open-source компонент с GitHub делает функцию лучше — использовать его. Если локальное решение заметно слабее облачного, честно описать разницу, но по умолчанию соблюдать требование автономной бесплатной работы внутри APK.

Главный критерий: не красивое обещание, а реально собираемое и работающее приложение/игра, которое можно установить на Android.
